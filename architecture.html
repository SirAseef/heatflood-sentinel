Modules, stream contract, alert engine & deployment profiles

HeatFlood Sentinel follows the five-layer design of the SRS (§4): ingestion → storage/processing → modelling → streaming inference & alerting → serving. Every runtime (local fallback, Kafka consumer, Spark foreachBatch) calls the same StreamProcessor and the same feature library used for batch training, so training and serving features cannot drift apart (train–serve parity).

Modules (src/hfs)

streaming processor (shared micro-batch logic), alert_engine, local_stream (replay + chaos), kafka_consumer, producer, spark_stream, live_feed, latency
api FastAPI app, read-only data access, token auth for ack/refresh
common config loader, schemas (pydantic ObsEvent), PKT time helpers, structured logging

Stream processing contract

Per micro-batch: schema/range validation (pydantic) → DLQ; dedup by deterministic event_id (UUIDv5 of city|time) within a 2-h watermark; late events beyond the watermark → DLQ; per-entity 36-day buffers; features from hfs.features.pipeline; heatwave evaluation once per completed PKT day (lead 1 d); flash-flood evaluation at the end of each 6-h window; XGBoost t2m +6/+24 h forecasts; alert engine; per-stage latency stamps. Checkpoint/restore covers dedup keys, buffers, open alerts and evaluated keys (exactly-once alert emission on restart, verified by the kill_restart chaos scenario).

Alert engine

Probability → level: Advisory ≥ 0.30, Watch ≥ 0.55, Warning ≥ 0.75, Emergency ≥ 0.90 (configs/alerts.yaml). Heatwave Warning additionally needs ≥ 2 consecutive hot days and Emergency ≥ 3; flood Emergency needs ≥ 100 mm/6 h. Escalation is immediate, de-escalation needs 2 consecutive lower evaluations, same-level re-notification waits 3 h.

Deployment profiles

  • dev-lite (executed): single process, local fallback queue, Parquet medallion, FastAPI + static dashboard.
  • docker compose (make up, provided, not executed in the sandbox): Kafka 3.7 KRaft, topic provisioning, API, replay + live producers, Python stream consumer; make up-full adds Spark 3.5 master/worker and the Structured Streaming job (infra/spark/submit.sh).

Reproducibility

Environment

  • Python ≥ 3.10 (developed on 3.12, CI on 3.11), CPU-only PyTorch is enough.
  • make setup installs requirements-dev.txt (core + pytest/httpx/ruff) and creates .env from .env.example.
  • Optional: requirements-stream.txt (kafka-python, pyspark), cdsapi for make data-cds, optuna for make tune, Playwright or a system Chromium for make screenshots.

One-command run

make setup
make reproduce      # data → features → train → benchmark → stream → live → scale → report
make api            # http://127.0.0.1:8000 (dashboard + /docs)

make reproduce needs internet access to Open-Meteo (archive + forecast). On the reference machine (2 vCPU, linux-arm64, CPU torch) the whole chain takes roughly 1.5–2 h; the slowest steps are SARIMA and the stream replay.

Determinism

  • Seeds: configs/models.yaml (seed: 42; LSTM daily also 7 and 2024). Torch uses 2 threads.
  • Splits are time-based and fixed in configs/app.yaml; climatologies and thresholds are fitted on train only.
  • Feature schema is hashed (feature_spec_hash in results/features_summary.json).
  • Event IDs are UUIDv5 of city|timestamp, so replays are idempotent.
  • Remaining nondeterminism: XGBoost hist multithreading and PyTorch CPU kernels can move metrics in the 3rd decimal. The live snapshot depends on the time it is run.

Tests

make test runs unit and integration tests on synthetic data only (no network): feature/label logic, metrics and statistical tests, alert-engine hysteresis/cooldown, ingestion validators, model smoke tests, and an end-to-end pipeline → stream → API test. make lint runs ruff.

Full-scale profile

make data-cds (ERA5 0.25°, 1991–2025, Copernicus account) plus make up-full (Kafka + Spark via docker compose) is the SRS full configuration. It is scripted but was not executed for v0.1.0 (DEVIATIONS.md D5, D6).
